## Stage 3 DSH integration design

- DSH `ToolRuntime.register()` at `packages/core/tools/src/index.ts:1037` validates the output declaration and delegates insertion to `ScopedLayers.effect(this.ctx, ...)`; the registration is therefore owned by the plugin fiber and returns an exact disposer. `ToolRuntime.get(name)` is the public read path for the real registration gate.
- The official local-plugin tutorial permits an absolute module path in a Loader patch and requires `inject = ['tools']`. The real-composition testing rule requires a test-only `cordis.yml` booted through Loader/app boot; a hand-built mock context alone is insufficient.
- The official tool tutorial uses `defineTool`, but `npm view @deepseek-ai/dsh-tools@0.1.0-rc.5` returned a real registry `E404`; the DSH tools package is not independently installable from npm at the pinned source version. The external bundle will therefore implement the documented `ToolDefinition` runtime fields directly and use the public `ctx.tools.register()` API, while tests validate the definition through the real DSH `ToolRuntime`.
- `@deepseek-ai/cordis@4.0.1` and `@deepseek-ai/schemastery@3.18.1` are published. Schemastery can provide load-time `receiptPath` and `maxBytes` validation without importing an unpublished DSH workspace package.
- Stage 3 surface is host-only and read-only: one zero-argument tool reads the configured already-completed JSON receipt, enforces a byte cap, validates every allowed field, and returns a newly projected summary. It never starts an audit, unloads a live plugin, reads session/model/tool history, or returns arbitrary JSON fields.
- There is intentionally no browser/client bundle. The real gate must prove bundle packaging, isolated D-drive profile installation/config composition, Loader activation, tool execution consistency with the receipt, precise disposal/removal, and zero skipped checks. Browser screenshots/GIFs and client HTTP/style/page-console gates are inapplicable and must not be fabricated.
- DSH `@deepseek-ai/dsh-app-boot` exports `boot(binName, absoluteConfigPath, patches?, prepare?, bareModuleBaseUrl?)`. It creates the real Cordis context, mounts Loader, mounts the root include, awaits Loader settlement, asserts every entry activated, and disposes the root fiber on startup failure. A test-only configuration containing the real SystemPrompt, ToolRuntime, and installed doctor module therefore supplies a keyless real-composition gate.

## Findings

1. **Zero-argument, model-uncontrollable input path — verified.** `src/dsh-plugin.ts:68` declares `parameters: { type: 'object', properties: {} }`; `execute` (line 75) and `output.render` (line 71) both discard the caller args (`_args`) and pass only `resolved.receiptPath` / `resolved.maxBytes` / `exec.signal` to `readReceiptSummary`. There is no code path by which a model-supplied value reaches `open()`, so no arbitrary-path read primitive exists. Minor: the parameter schema omits `additionalProperties: false`, which is inconsequential because args are never read.
2. **Read-only — verified.** `src/receipt-viewer.ts:265` is the only filesystem call in either in-scope source file: `open(path, 'r')`, with `file?.close()` in `finally` (line 287). No write/rename/unlink, no audit invocation, no `ctx.registry`/loader/plugin-unload call, no session/profile/credential access. `apply` (line 80-82) touches only `ctx.tools.register`.
3. **Bounded — verified.** `MAX_RECEIPT_BYTES = 16 MiB` (line 8) caps the schema (`Schema.natural().min(1).max(MAX_RECEIPT_BYTES)`, default 1 MiB) and is re-checked imperatively in `resolveConfig` (lines 51-53); `timeoutMs` is constrained to 1..60000 and passed to `timeoutMs` on the definition. The reader allocates `maxBytes + 1` and rejects with `RECEIPT_TOO_LARGE` when `offset > maxBytes` **before** `JSON.parse` (lines 267-277, then 297). `signal?.throwIfAborted()` is checked before `open` and inside every read iteration. `Buffer.allocUnsafe` is safe here because only `subarray(0, offset)` is decoded.
4. **Strict schema / no field leakage — verified.** Every object level uses exact-key enforcement (`exactKeys`, `exactKeysWithOptional`, lines 72-95) including nested `phases[].resources[]` and `errors[]`; enums are closed sets built from `EXIT_CODES` keys and literal phase/category lists (lines 13-15, cross-checked against `src/contracts.ts:8-45`); `sourceHash` must match `/^[0-9a-f]{64}$/`; integers must be safe integers with correct minimums; `exitCode !== EXIT_CODES[outcome]` is rejected (line 192). Crucially, `parseReceipt` returns a freshly constructed object literal rather than spreading input, and `summarizeReceipt` re-projects again while dropping `runtime.modulePath` (lines 236-260). Unknown fields, raw JSON, and the host module path therefore cannot reach the tool output. Invalid UTF-8 (`TextDecoder(..., { fatal: true })`) and invalid JSON get distinct sanitized codes.
5. **Fail-loud before registration — verified.** `createReceiptTool` calls `resolveConfig` as its first statement (line 62), and `apply` passes `createReceiptTool(config)` directly as the `register` argument, so any unsafe config throws before `ctx.tools.register` is invoked. `tests/dsh-plugin.test.ts:38-51` covers relative path, oversized `maxBytes`, and zero `timeoutMs`.

No module-level mutable registry state and no registration on any context other than the injected `ctx`, so nothing survives plugin disposal on the product side. The returned disposer is intentionally discarded, which is correct only if DSH's `ctx.tools.register` is itself a Cordis effect — see Evidence Gaps.

It would parse and project cleanly, and the summary would omit its `modulePath` (`D:\knowledgeBase\deepseek-harness\vendor\...`).
10. **Non-blocking hygiene issue: error `cause` chains retain the host path.** `RECEIPT_READ_FAILED`/`RECEIPT_INVALID_JSON`/`RECEIPT_INVALID_UTF8` carry `{ cause }` (lines 226, 281, 285). The sanitized `message` is constant, but a Node `ENOENT` cause embeds the absolute receipt path, and `util.inspect` of an error prints the cause chain. If DSH surfaces raw errors to the model, the configured host path could be disclosed. Low severity (admin-configured path, no attacker control), but it is the one place where the "no path in errors" intent depends on DSH-side error rendering.
11. **Non-blocking: unknown-key names are echoed in validation messages.** `invalid(\`${path}.${key}\`)` (line 75) interpolates the offending key name from the file into `RECEIPT_INVALID_SCHEMA`. Values never leak (`tests/receipt-viewer.test.ts:70-78` asserts this), and a key name grants no capability beyond what allowed string fields (`label`, `identity`, `fixture`, `limitations`) already return by design from a trusted, doctor-written file — so this is a hardening note, not a leak of untrusted-controlled data beyond the existing trust boundary.

No blocking defect was found in the reviewed scope: no arbitrary-path read, no extra-field leakage into the summary, no model-controlled input path, no active-profile mutation, no live-target unload, no second Web/React surface, and no missing product-side disposer.

## Residual Risks

1. Error `cause` chains may disclose the configured absolute receipt path (and thus `DSH_HOME` layout) if DSH inspects or logs errors verbatim; consider dropping `{ cause }` on the model-facing path or mapping to code-only errors.
2. `RECEIPT_INVALID_SCHEMA` messages echo unknown key names from the receipt file; harmless under the current trust model but worth truncating/eliding if the receipt file's trust level ever weakens.
3. Output volume is bounded only indirectly: a valid 1 MiB receipt with many resources yields a correspondingly large summary (`phaseCounts` is aggregated, but `delta.added`/`delta.removed`/`errors`/`limitations` are passed through element-for-element). No entry-count cap exists; this is a context-cost and verbosity risk, not a confidentiality one.
4. `isConcurrencySafe: () => true` combined with `Buffer.allocUnsafe(maxBytes + 1)` allows several concurrent allocations up to the configured cap (default 1 MiB, ceiling 16 MiB). Bounded per call, but concurrency multiplies peak memory.
5. The tool's read-only and disposal guarantees remain contingent on DSH's `ToolRuntime` honoring effect-owned registration and not re-validating/expanding `parameters`; drift on the DSH side would silently weaken both the zero-argument and no-live-unload claims. This is the item the next round's Loader/gate review should close.
6. Correctness of the reviewed reader is asserted against `RECEIPT_SCHEMA_VERSION = '1.0.0'` only; any producer-side schema change without a version bump would be rejected fail-closed (safe direction), but would break the tool until both sides are updated.
